# RC-02 — Tenant-isolated operator workflow (synthetic only)

This change is **stacked on RC-01 Draft PR #1** and is not production-ready.

## Objective

Add a minimal, authorized human ticket workflow for residential-community operations without ingesting or persisting any residents' chat content, phone numbers, personal names, apartment numbers or files.

Implemented prototype:
- Strict offline JWT validation with injected issuer, audience, signing key and expiration.
- Tenant ID and operator role read **only from signed JWT claims**, never request-controlled tenant parameters.
- Explicit allowed-tenant list (fail-closed); absent/invalid operator configuration exposes no endpoints.
- Operator/supervisor roles. A human supervisor must authorize ticket resolution.
- Tenant-isolated PostgreSQL persistence; parameterized queries and transaction-local tenant identity.
- Forced PostgreSQL row-level security, backed by a **dedicated non-owner, non-superuser, no-BYPASSRLS runtime role**.
- Metadata-only tickets and HMAC-pseudonymized audit actor identity.
- Optimistic version checks, synthetic HTTP and live ephemeral PostgreSQL CI tests.
- No integration with RC-01 webhook processing, no Telegram outbound actions, no LLM/embedding/vector/analytics services.

## Endpoint contract

Under /operator/v1/tickets (enabled only with valid configuration):
- POST / with exact JSON {"category":"Water","priority":"Urgent"}; creates ticket without free-text. Urgent tickets start in **Escalated**, requiring human handling.
- GET /{ticketId}; returns 404 for other-tenant tickets exactly as for absent tickets.
- POST /{ticketId}/escalate with {"expectedVersion":1}; authorized human operator or supervisor; only valid state transition.
- POST /{ticketId}/resolve with {"expectedVersion":1}; human **supervisor** role only.

Categories: Heating, Water, Electricity, Elevator, CommonArea, Other.
Priorities: Routine and Urgent.
Allowed statuses: Open -> Escalated -> Resolved; a supervisor may also resolve Open. No automatic closure.

## Data minimization and retention design

PostgreSQL stores:
- tenant UUID, random ticket UUID, enum category, priority, status, version and timestamps;
- audit event type, pseudonymous HMAC actor hash, creation timestamp and corresponding ticket/tenant IDs.

No resident identification or chat messages in current schema. This **reduces** sensitivity but does not guarantee that all records are anonymous (timestamps, cross-system correlations, and operational context can identify people). Treat databases and backups as restricted.

Before real use, the customer must approve the lawful basis / transparency notice, data-controller roles, access controls, data-subject handling, exact retention periods and deletion method. No default retention policy is activated yet; **RC-02 is synthetic-only**. A later migration will implement time-based retention and verified backup expiry.

## Operational secret configuration (examples only; never in git)

Required environment-variable names:
- ResidentChat__Operator__Enabled
- ResidentChat__Operator__Issuer
- ResidentChat__Operator__Audience
- ResidentChat__Operator__JwtSigningKey
- ResidentChat__Operator__AuditHmacKey (separate from signing key)
- ResidentChat__Operator__ConnectionString
- ResidentChat__Operator__AllowedTenantIds__0 etc.

All operator values except Enabled and empty AllowedTenantIds are intentionally absent from default appsettings. The application does **not** issue JWTs. Production identity onboarding, key rotation, revocation and secure hardware/secret storage require an explicit customer-approved design. TLS termination and an egress-deny firewall are mandatory before exposure.

Run migration db/migrations/001_ticket_workflow.sql with a **separate** migration owner. Runtime account needs USAGE on schema; SELECT/INSERT/UPDATE tickets; SELECT/INSERT audit; and USAGE/SELECT on audit identity sequence. The runtime account must not have ALTER / DELETE / table ownership, elevated privileges or BYPASSRLS.

## Test contract

GitHub Actions runs two CI suites on RC-02 branch:
- RC-01 synthetic Telegram webhook HTTP gate (inherited);
- RC-02 synthetic JWT + real PostgreSQL/row-level security + two-tenant HTTP gate.

CI PostgreSQL credentials and JWT values are fixed **synthetic** fixtures, never usable in real services. No external AI invocation and no actual residents.

## Known blockers / limitations

- No customer identity provider or operator accounts are configured.
- The tickets are metadata-only; proper consented contact or location resolution is a separate future design.
- RLS isolation is verified with a dedicated restricted CI role; privileged migration accounts can bypass it.
- An application-local JWT issuer/signing secret is a prototype trust anchor; identity, rotation and session lifecycle require further hardening.
- No HTTP rate limits, incident notification channels, deployment firewall checks, durable RC-01 ingress dedup or backup/retention enforcement yet.
- Important: never merge and deploy directly from green CI. Security review and explicit authorization remain required.
